# Creative-workflow patterns

## Portable stage map

Use only the stages the project needs:

`intake → explore → establish canon → plan → draft → structural revision → scene revision → line revision → package → publish/archive`

Every stage should define:

- required inputs;
- records it may read;
- output destination;
- human decision;
- canon-promotion rule;
- version or backup point;
- next valid stages.

## Record scopes

| Scope     | Appropriate contents                                               |
| --------- | ------------------------------------------------------------------ |
| Global    | Author preferences genuinely needed across projects                |
| Series    | Shared setting, recurring characters, chronology, terminology      |
| Project   | This work's cast, plot, locations, themes, style, constraints      |
| Chapter   | Local arc state, summaries, goals, dependencies                    |
| Scene     | Viewpoint, intent, setting, participants, turn, outcome, aftermath |
| Temporary | Candidate ideas, extracted facts, critiques, alternate drafts      |
| Private   | Spoilers, hidden motives, future reveals, author-only decisions    |

“Always include” is a cost decision, not an importance badge.

## Operation contract

For each prompt or platform action, record:

- operation name and purpose;
- accepted source types;
- exact context selectors;
- whether it may invent, rearrange, edit, or only extract;
- expected output shape;
- temporary or canonical destination;
- acceptance checks;
- failure and rollback behaviour.

## Promotion ladder

Use explicit state changes:

`generated candidate → author-reviewed proposal → approved working record → established canon`

Do not skip directly from extraction or brainstorming to canon.

## Version and status pattern

Keep content version separate from workflow status. Example statuses:

- idea;
- planning;
- drafting;
- structural edit;
- scene edit;
- line edit;
- ready to package;
- published;
- shelved;
- archived.

Use immutable accepted checkpoints rather than relying only on labels such as “latest” or an array index.

## Transformation checks

After outline-to-scene, import, extraction, summarisation, or rewrite:

- compare identifiers and item counts;
- identify omitted, merged, split, invented, or reordered material;
- sample the beginning, middle, and end;
- verify viewpoint, chronology, unresolved threads, and knowledge boundaries;
- review high-impact changes manually;
- retain the source and rejected outputs.

Word-count similarity alone does not prove fidelity.

## Platform adaptation

For Novelcrafter-like systems, distinguish codex/story-bible records, plan hierarchy, scene beats, manuscript prose, summaries, snippets, custom prompts, provider profiles, and exports. Confirm current UI behaviour in the official documentation before giving click-by-click instructions.

The reusable principle is scoped structured context plus human-controlled promotion, not any one platform's category names or subscription tier.

## Mechanics boundary

Optional rules can track fictional arousal, injury, attraction, influence, pregnancy, reputation, or other states. Keep those state machines:

- opt-in at the project or session level;
- transparent to participants;
- reversible or adjustable by agreed rules;
- separate from real consent and player authority;
- unable to dictate player-character interiority unless explicitly delegated;
- labelled as fictional mechanics, not psychology or biology evidence.
